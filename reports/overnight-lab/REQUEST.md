# いれーな REBORN — 一晩自走ミッション：20階層実験キャンペーン／バランス研究

## 最重要の依頼
あなたは「いれーな REBORN」の実験場開発担当兼QA担当です。既存の最新版コードを分析し、**実験場限定の20階層キャンペーンを、実際に遊べる試作品として実装・テスト・ビルド・納品**してください。ユーザーが就寝している間、合理的な判断は自走して構いません。ただし本編採用の判断はユーザーに残してください。

**重要：現在別件の通常戦闘UI改修が進んでいます。その成果を含む最新版作業ツリーを先に確認してください。古いソースZIPで上書きしないこと。** 未コミットの作業、ほかのCodexタスクと競合する変更があれば安全なコピー／独立ブランチ・ワークツリーを作り、元の作業を保護すること。初期状態とコミットID／ソース版を記録し、不明ならその旨記すこと。

## 目的とゲームデザインの優先順位
- 本編の通常100階層は現状維持。20階層への置換は**今回は禁止**。
- 20階層版は、**通常編をテンポよく進め、ステラ／EXカイザーといった目玉ボスを早めに楽しめる設計**の試作品。通常20階層すべてを長期の苦行にしない。
- Lv.1〜5は爽快な導入、Lv.6〜10は育成／技の使い分け、Lv.11〜15は権能／刻印の組み合わせ、Lv.16〜19は短い応用、Lv.20は通常編の区切り。これは作業仮説で、現行ソースの実情と実測に合わせ微調整してよい。
- 攻撃予告、次行動予測、ダメージ予測UIは**追加禁止**。未来を表示せず、実際に起きた行動・状態をログで説明する方向。
- **羽弾の確定仕様（黒翼による最終5倍等）を本編で勝手に弱体化・削除しない。** 実験場では別設定として複数の調整案を比較可。調整の採否は未確定とする。
- UIはスマホ縦画面を最優先。前回の対峙イラスト風味は参考だが、無駄な装飾や長大なスクロールを増やさない。存在しないMP/TP等を発明しない。

## 許可する範囲
- 実験場に**明確に「試作」「本編非反映」と表示した独立モード**を追加。
- 実験用の難易度データ／敵配置／報酬／解放シミュレーション／戦闘ルールを分離して実装。複数案の比較も可。
- 実験場内だけに限った技の役割差別化、敵の行動バリエーション、ゲージ／CT／報酬設計を検証し、その結果を整理。
- 不足するアセットは既存素材や無理のないCSS代替を優先。ユーザー未承認の新画像が必須なら適当な別人画像で埋めず、納品レポートに要件として記載。
- QA／再現用スクリプトや必要最小限のテストを追加。

## 絶対に守る境界
1. 本編の100階層、ステラ・EXの既存解放順序、進行済みユーザーのセーブ、通常報酬、実績、既存ボス、三相決戦試作を壊さない。
2. 実験場の挑戦結果・報酬・勝敗・実績・解放は**本編データへ混入させない**。実験終了／再読み込み時の状態も検証する。既存の実験場での「独立試験」の設計を先に調査し、極力再利用する。
3. 現行で動作している通常戦闘UI改修を上書きしない。古いZIPに戻さない。
4. セーブ互換性・既存の確定倍率・ユーザー入力・既存操作を無断変更しない。通常戦闘の羽弾／穿羽／連羽の刻印表示切り替えは別作業の成果を保護し、競合したら優先的に維持する。
5. 無関係なリファクタリング、デザイン刷新、ホームUIや課金・広告機能の追加をしない。ネットワークへの公開や本編マージは**明示承認なしで行わない**。
6. テストの削除・緩和、エラーの握りつぶし、未実施検証の成功報告を禁止。
7. ユーザーが寝ているため質問への即答を期待しない。判断できるものは実験場限定の可逆的な仮仕様として決め、報告に明記。**保存や進行の破壊リスクがある未確定事項は実装せず保留**。

## 必須工程（順番を守る）
### Phase 0：現状確定／作業場所の隔離
- `README.md`, `package.json`, `web/src`, `tests`, `tools`, 既存の実験場と戦闘計算を調査。実際のルート・コマンド・セーブキー・解放条件を記録。
- `git status` や作業場所を確認。専用ブランチ／ワークツリーまたは安全なコピーで進め、現在進行中のUI変更を保護。
- 変更開始前に可能な範囲で `npm run check`, `npm test`, `npm run build` のベースラインを取得。既存の失敗があれば区別して報告。

### Phase 1：本編バランスの基準計測
- 既存の `reports/balance-audit.md` を参考にしつつ、**最新版コードで再測定**。
- Lv.1, 2, 5, 10, 15, 20, 25, 50, 100 の進行と技選択を比較（到達可能な状態・必要な解放を現行コードに即して設定）。
- 羽弾優先／斬撃優先／権能・必殺活用／防御を交えた戦法を、同一初期条件・同一乱数シードで比較。
- 勝率、平均／最大ターン、技の使用頻度、必殺発動回数、被ダメ、育成投資、報酬など**測定可能な指標だけ**集計。サンプル数と測定条件を明示。架空の結果は禁止。
- Workの初見評価（Lv.2で斬撃66・権能179・羽弾726、序盤Lv.1/3/4/5は羽弾一撃）を、**別環境での参考報告**として扱う。最新版で再現するか確認し、再現不可なら区別する。

### Phase 2：20階層の試作設計と実装
- 通常20階層の短期攻略に最適化した敵ステータス、節目戦、報酬、必要な育成コストを設計。単純なHP倍率20段階ではなく、技の使い分けが自然に生じる変化をつける。
- ステラ／EXに早く進むことを主題にした**独立した実験用ルート**を設ける。既存の本編解放フラグに触れない。既存のステラ／EX本体を使う場合も、試験データ上でのみ挑戦させる。実装負担や既存仕様を保護する必要があれば、20階層終了時に「試作ルート完了」として本編解放は行わず、レポートで接続案を提案してよい。
- 実験場から入り、試作であることと本編セーブ・報酬非反映を明記。ホーム、本編冒険ボタン、ワープ処理を上書きしない。
- 初見でも分かる短い説明／効果表示を入れる。未来の敵行動予告は入れず、起きた結果のログは正確に説明。
- バランスを複数パターンで試し、実測に基づいて最も遊びやすい案を試作品に採用。試さなかった案もレポートに残す。

### Phase 3：品質検証と安全確認
- 本編の全テスト・構文チェック・ビルドを実行。新しい実験場専用テストも追加。
- 本編の100階層クリア、Lv.100→ワープ→ステラ→EXの既存進行や、既存の試験モード、保存互換の関連テストを実行。
- 実験場から本編へ報酬・実績・解放が漏れないこと、途中撤退・再試行・敗北・再読込時に壊れないこと、UI改修と競合しないことを検証。
- Playwrightなど利用可能ならスマホ相当の320/375/390/430px幅、タップ領域、技表示、画面の重なり、ログの高さを確認。Chromium/WebKit環境がなければ実行できた範囲を正確に報告。
- 失敗したら原因究明→修正→再検証。**テストを外して成功扱いしない**。
- ビルド成果物とソース差分の整合性を確認。実機Safariでの確認は、実際に行わなければ「未確認」と記載。

### Phase 4：成果物と報告
- 操作できるHTML（可能なら単体 `irena-play.html`）、最新版ソースZIP、実験場モードの遊び方を納品。ファイル添付・サイズ上限に合わせ、必要なら画像と指示書を分離し、古いビルドを同梱しない。
- `reports/overnight-lab/PROGRESS.md` を進捗／復旧用に残す。節目ごとに更新し、作業が中断しても次回読めば続けられるようにする。
- `reports/overnight-lab/REPORT.md` に以下を必ず記載：
  1. 作業開始時のソース版／保護した作業
  2. 変更ファイル一覧／主な変更点
  3. 通常20階層の意図・試作数値・設計理由
  4. 初期条件／乱数シード／サンプル数を伴うバランス測定表
  5. 戦略別の勝率・ターン・技使用頻度、採用／保留した案
  6. 本編との差分、セーブ独立性、元の100階層を維持した確認
  7. テスト・構文チェック・ビルド・ブラウザ検証の**実行結果**
  8. 未解決事項・ユーザーが採用判断すべきこと
  9. **追加で欲しい画像素材**：必要なものがあれば用途、枚数、サイズ、縦横比、透過要否、人物の設定、構図、雰囲気を具体的に。なければ「現時点で必須素材なし」と明記。
- 完了の定義：要求仕様が満たされ、関連テスト＋ビルドが成功し、本編保護と変更範囲を検証できた状態。未達なら**未完了**と明示し、再開手順を残す。

## 利用枠と中断への対応
- 利用可能な範囲内で、追加承認不要の安全な調査・実装・再試行は自律的に進めてよい。
- APIや有料サービスに勝手に課金しない。利用上限を回避しようとしない。上限・時間切れ・承認待ちで止まったら、その時点で変更を保全し、PROGRESS.mdに「現状、テスト結果、次の一手」を記載。
- 長時間ずっと一つの試行に固執しない。実装の節目で動作する状態を確保し、小さくコミットする（利用可能な作業ツリーの場合）。
- ユーザーの朝の最初の操作が**実際に遊んで評価できること**を最優先とする。重大な仕様変更を断定的に本編へ採用しない。

## 起動時にやること
1. 最新ソースと現在のCodex作業の状態を確認
2. 別の戦闘UI改修がまだ未完了なら競合箇所を避け、安全な隔離を優先
3. 調査→実測→実験場試作→回帰テスト→納品まで、無理なく実行
4. 途中で使う画像が足りなくても手を止めず、既存アセットで暫定表示し、最後に画像要件を列挙

**ユーザーからの追加判断が得られない間は『実験場限定・可逆・本編に無影響』を最優先原則にして自走すること。**
